\begin{abstract}
Software architecture descriptions can diverge from the source code they are intended to govern. This paper presents ArchSync, a deterministic architecture-conformance prototype that treats a machine-readable architecture model as an executable contract and reconstructs an observed service graph from TypeScript source code. Stack-specific analyzers detect selected HTTP, PostgreSQL, Redis, and AMQP interactions; a conformance engine then classifies a repository as no-impact, rule violation, or architecture evolution and attaches model and file-line-column evidence. We evaluate the prototype on a controlled Order Platform benchmark containing one baseline and ten independently applied patches: five no-impact changes, three violations, and two evolutions. Across the ten patched repositories, full-graph node and edge detection produced 53 and 54 true positives with no false positives or false negatives; changed-graph detection produced three node and six edge true positives with no errors. ArchSync classified 10/10 cases correctly, matched the expected violated-rule set in 3/3 violation cases, and matched both the expected file and an exact source line in 5/5 finding-bearing cases. The baseline and all cases produced byte-identical normalized results across duplicate executions. These results establish feasibility on a small development benchmark, not general accuracy: the benchmark and analyzer were co-developed, the system is synthetic, and only explicit TypeScript/Node.js patterns are covered.
\end{abstract}

\section{Introduction}

Software architecture captures the intended decomposition of a system, the responsibilities of its components, and the relationships that are permitted between them. As systems evolve, this intent can diverge from implementation; surveys of architecture erosion report both structural violations and broader effects on maintenance and evolution \cite{desilva2012erosion,li2022erosion}. A locally reasonable change can bypass a gateway, couple an interface directly to a database, or introduce infrastructure without an explicit architecture decision while compilation and functional tests continue to pass.

The underlying problem is not the absence of documentation alone. It is the absence of a deterministic, evidence-backed connection between architecture intent and implementation. A diagram can communicate the desired system but is difficult to use as an automated quality gate. Conversely, a source-derived dependency graph can expose implementation relationships but does not by itself state which relationships are allowed, forbidden, required, or merely require review.

We present ArchSync, an architecture-conformance workflow based on two graphs. The expected graph is derived from a versioned \texttt{architecture.yaml} document containing components, relationships, and deterministic rules. The observed graph is inferred from source code by stack-specific analyzers. ArchSync compares the graphs and produces one of three classifications: \emph{no-impact} when implementation conforms without topology changes, \emph{violation} when one or more rules are broken, and \emph{evolution} when a non-forbidden topology change requires human review. Findings retain both the model location that establishes the expectation and the source location supporting the observation.

The prototype deliberately focuses on TypeScript and Node.js. It recognizes HTTP calls through \texttt{fetch}, PostgreSQL access through \texttt{pg}, Redis operations, and AMQP publishing and consumption. This bounded scope permits deterministic contracts and reproducible measurement without probabilistic inference. Large-language-model explanations and automatic repairs are excluded from the decision path.

This paper makes the following contributions:
\begin{itemize}
  \item a machine-readable architecture contract with typed components and relationships plus deny, allow, require, and require-path rules;
  \item a deterministic TypeScript source-to-graph pipeline with file, line, column, detector, snippet, and confidence evidence;
  \item a three-way decision model separating violations from topology evolution; and
  \item a reproducible controlled evaluation whose machine-readable artifact binds the model, baseline, patches, dependencies, outcomes, and result through SHA-256 provenance.
\end{itemize}

\section{Background and Related Work}

\subsection{Architecture Erosion and Reconstruction}

Architecture erosion denotes progressive misalignment between intended architecture and implementation. De Silva and Balasubramaniam organize erosion-control work into strategies that minimize, prevent, or repair erosion and argue that no single strategy is sufficient \cite{desilva2012erosion}. A later systematic mapping study covering 73 primary studies reports that erosion manifests through architectural violations and structural problems and also affects software quality and evolution \cite{li2022erosion}. These findings motivate continuous, implementation-linked checks while cautioning against reducing architecture quality to a single structural metric.

Software architecture reconstruction addresses the related problem of recovering architectural views from implementation artifacts. Ducasse and Pollet distinguish bottom-up, top-down, and hybrid reconstruction processes \cite{ducasse2009reconstruction}. ArchSync is narrower than general reconstruction: it starts from an explicit expected model and extracts only a defined set of service and infrastructure relationships needed for conformance decisions.

\subsection{Static Architecture Conformance}

Software Reflexion Models compare a high-level model with a source-derived model and identify convergence, divergence, and absence \cite{murphy1995reflexion}. Knodel and Popescu compare reflexion models, relation conformance rules, and component access rules across 13 dimensions, showing that static conformance has multiple useful but non-equivalent formulations \cite{knodel2007comparison}. Dependency Constraint Language (DCL) expresses allowed and forbidden dependencies for object-oriented systems and statically detects silent architectural erosion \cite{terra2009dcl}.

ArchSync inherits the central expected-versus-implemented comparison from this line of work. Its prototype-specific contribution is an operational combination for TypeScript service topology: typed HTTP, data, and asynchronous edges; explicit require and require-path semantics; source and model evidence in a versioned finding contract; and separate violation and evolution outcomes. The work does not claim that expected-observed graph comparison or dependency constraints are new.

\subsection{Conformance in Continuous Integration}

Pinto et al. integrate DCL-based conformance into Jenkins and report an industrial-style Java evaluation in which 44 constraints were introduced across six releases and 42 detected violations were corrected before the following release \cite{pinto2017archci}. This demonstrates the value of moving conformance into the integration loop. ArchSync Phase 2 stops one layer earlier: it establishes deterministic analysis, evidence, and benchmark contracts. Pull-request annotations and merge-gate automation remain future work, so the present evaluation concerns detector and decision correctness rather than CI adoption or developer behavior.

\section{Problem Definition}

Let the expected architecture contract be
\begin{equation}
  M = (C_E, E_E, R),
\end{equation}
where $C_E$ is the set of expected components, $E_E$ is the set of expected typed and directed relationships, and $R$ is the set of conformance rules. We denote the graph projection of this contract by $G_E=(C_E,E_E)$. A relationship is represented as a tuple $(u,t,v)$, where $u$ is the source component, $v$ is the target component, and $t$ is the relationship type.

Given a source-code repository $S$, a stack-specific analyzer $A$ constructs an observed graph
\begin{equation}
  G_O = A(S) = (C_O, E_O, P),
\end{equation}
where $C_O$ and $E_O$ are observed components and relationships, and $P$ maps each observation to source evidence. Source evidence contains a repository-relative file path, line, column, detector identifier, excerpt, and confidence value.

ArchSync supports four deterministic rule semantics. A \emph{deny} rule rejects every matching relationship. An \emph{allow} rule constrains the outgoing relationships of selected sources to an allowed target set. A \emph{require} rule states that every matching source must have a direct edge to a matching target. A \emph{require-path} rule states that every matching source must reach a matching target through a non-empty directed path. Rules may optionally constrain the relationship type and may use wildcard component selectors.

The conformance function compares $M$ and $G_O$ and returns a graph difference $\Delta$, a set of rule violations $\mathcal{V}$, and a set of evidence-backed findings $\mathcal{F}$. Its classification is defined as
\begin{equation}
\operatorname{class}(M,G_O)=
\begin{cases}
\text{violation}, & \text{if } |\mathcal{V}| > 0,\\
\text{evolution}, & \text{if } |\mathcal{V}| = 0 \land |\Delta| > 0,\\
\text{no-impact}, & \text{otherwise.}
\end{cases}
\end{equation}

The research problem is to determine whether an implementation-level analyzer can reconstruct enough architectural information to make this classification accurately, reproducibly, and with actionable evidence. A useful solution must minimize both missed architectural relationships and spurious relationships, preserve stable outputs for identical inputs, and separate rule-breaking changes from topology changes that may be valid but require approval.

\section{Research Questions}

\textbf{RQ1: How accurately can ArchSync reconstruct software architecture components and relationships from TypeScript source code?}

This question measures precision, recall, and F1 score for complete observed graphs and for nodes and edges changed by a patch.

\textbf{RQ2: How accurately can ArchSync distinguish no-impact changes, architecture-rule violations, and architecture evolution?}

This question evaluates exact classification agreement with a manually curated ground truth and, for violations, agreement on the expected rule identifiers.

\textbf{RQ3: How accurately can ArchSync localize architectural findings in source code?}

This question evaluates whether a finding identifies the expected changed file and exact source line. Column, detector, excerpt, and model path are retained as additional diagnostic evidence.

\textbf{RQ4: Are ArchSync outputs deterministic and reproducible for identical model and repository inputs?}

This question compares serialized observed graphs and findings across repeated executions and across clean installations on supported operating systems.

\section{Proposed Approach}

\subsection{Architecture as an Executable Contract}

ArchSync uses a YAML document as the source of truth for architecture intent. The model defines stable component identifiers, component types, layers, directed relationships, rule severity, ownership metadata, and optional quality goals. JSON Schema validation rejects malformed documents, while semantic validation rejects unknown component references, duplicate edges, invalid identifiers, and other topology inconsistencies. Mermaid and draw.io views are derived from the model; they are not independent sources of truth.

The validated model is converted into an expected graph with stable node identifiers and canonical edge keys. This normalization makes graph comparison and evidence manifests reproducible. It also enables the same conformance semantics to be used by command-line tools, benchmark evaluation, and future continuous-integration adapters.

\subsection{Source-to-Graph Analysis}

A Guardian analyzer traverses TypeScript files under component roots and parses them through the TypeScript Compiler API. Rather than matching arbitrary text, detectors inspect syntax-tree nodes, imports, call expressions, variable initialization, environment-variable references, and URL literals. Stack-specific detectors translate these signals into typed architectural relationships.

The initial detector set recognizes HTTP requests, PostgreSQL clients and queries, Redis clients and operations, and AMQP publishing and consumption. Endpoint resolution uses explicit literals and deterministic environment-variable fallbacks when available. Every detected relationship carries one or more source locations. Detected components and relationships are sorted and deduplicated before serialization.

\subsection{Conformance and Decision Semantics}

The conformance engine first computes node and edge differences between the expected and observed graphs. It then evaluates the observed graph against the architecture rules. A rule violation takes precedence over ordinary topology evolution. This precedence prevents a forbidden new edge from being reported only as an architectural change.

The repository-facing decision is derived from the classification:
\begin{itemize}
  \item \textbf{PASS} for no-impact changes;
  \item \textbf{BLOCK} for deterministic rule violations; and
  \item \textbf{REVIEW} for non-forbidden architecture evolution.
\end{itemize}
The REVIEW outcome is important because a new component or relationship is not necessarily incorrect. ArchSync reports the change without automatically modifying the approved architecture contract.

\subsection{Evidence-Rich Findings}

A finding contains a stable contract version, identifier, kind, severity, message, optional rule identifier, affected component or edge, source evidence, and model evidence. For an observed forbidden edge, the evidence points to the call site that introduced the relationship. For a missing required edge or path, the source component is used as a deterministic anchor and the relevant rule location is retained as model evidence.

This separation allows the deterministic engine to state \emph{what} changed and \emph{why} it violates the contract, while preserving enough context for a developer or architect to inspect the implementation.

\section{Implementation}

\subsection{Implemented Prototype}

The implementation is divided across three repositories used in this study. \texttt{archsync-core} implements Architecture Model version 0.1, JSON Schema and semantic validation, normalized graphs, graph difference, deny/allow/require/require-path semantics, command-line reports, and deterministic Mermaid and draw.io projections. Its verification suite contains 83 tests and reports 98.89\% statement coverage, 91.97\% branch coverage, 100\% function coverage, and 98.89\% line coverage.

\texttt{archsync-guardian} implements Observed Graph and Finding Contract version 0.1. The analyzer traverses TypeScript files, maps component roots, parses syntax trees through the TypeScript Compiler API, resolves explicit literals and selected environment-variable fallbacks, runs HTTP/PostgreSQL/Redis/AMQP detectors, captures evidence, and sorts and deduplicates output. Guardian delegates graph difference and rule semantics to Core. Its verification suite contains 22 tests and reports 96.59\% statement coverage, 89.57\% branch coverage, 97.56\% function coverage, and 96.59\% line coverage.

\texttt{archsync-benchmark} provides the Order Platform baseline, ten real unified-diff patches, the ground-truth manifest, integrity validation, mutation tests, and the evaluation runner. Each patch is applied to a fresh temporary copy of the baseline. The benchmark suite contains 14 invariant and mutation tests. \texttt{archsync-mcp} is not used in the experiment.

\subsection{Reproducibility Controls}

The benchmark pins Core commit \texttt{304f4ac48137} and Guardian commit \texttt{e1cd98956856}. The manifest records SHA-256 values for the architecture model, nine-file baseline tree, and ten-patch set. The generated evidence additionally hashes the manifest and normalized result and records explicit denominators for classification, rule-set, evidence, and determinism measures.

We executed the complete verification commands from clean repository clones on Windows with Node.js 22.16.0 and pnpm 11.16.0. The clean working trees remained unchanged after installation and verification. Core passed 83/83 tests and 13/13 CLI smoke checks; Guardian passed 22/22 tests and 7/7 CLI smoke checks; the benchmark passed 14/14 tests, validated all 10 patches, and reproduced the committed result. After packaging the pinned Core and Guardian revisions as SHA-256-verified runtime artifacts, GitHub Actions also ran the complete benchmark gate from clean \texttt{ubuntu-latest} and \texttt{windows-latest} checkouts at benchmark commit \texttt{278019c06929}; both jobs passed, including all 22 analyzer executions and the evidence-drift check.

\section{Evaluation Methodology}

\subsection{Experimental Object}

The experiment uses a controlled Order Platform implemented in TypeScript and Node.js. Its expected baseline contains five components and five directed relationships. Ten patches are distributed as five no-impact changes, three rule violations, and two architecture evolutions. They include internal refactoring, forbidden service bypasses, removal of a required dependency, addition of Redis, and introduction of AMQP communication.

Each case declares changed files, expected graph delta, classification, findings, and source location. The topology labels and classifications originated in Phase 1. Patch implementations and exact evidence lines were refined while the Phase 2 analyzer was integrated. The resulting artifact is therefore a development benchmark and regression oracle, not a blinded holdout set. Validators check structural consistency, patch applicability, changed-file membership, patch-hunk containment, and integrity hashes; they do not replace independent semantic review.

\subsection{Procedure}

The executed procedure was:
\begin{enumerate}
  \item validate the expected architecture, ground-truth manifest, hashes, and all patch applications;
  \item analyze the unchanged baseline twice;
  \item for each case, copy the baseline into a fresh temporary directory and apply exactly one patch;
  \item analyze the patched repository twice;
  \item compare predicted nodes, edges, classification, violated rule identifiers, and source evidence with ground truth; and
  \item remove the temporary directory before the next case.
\end{enumerate}

This protocol performs 22 analyzer executions per evaluation: two for the baseline and two for each of ten cases. Repeated results are compared as normalized JSON. Reproducibility is checked locally and in CI. The benchmark workflow installs SHA-256-verified runtime packages and executes the full protocol from clean \texttt{ubuntu-latest} and \texttt{windows-latest} checkouts; both jobs passed for benchmark commit \texttt{278019c06929}.

\subsection{Metrics}

For node and edge detection, true positives, false positives, and false negatives are aggregated across cases. Precision, recall, and F1 are
\begin{align}
  \operatorname{Precision} &= \frac{TP}{TP+FP},\\
  \operatorname{Recall} &= \frac{TP}{TP+FN},\\
  F_1 &= 2\cdot\frac{\operatorname{Precision}\cdot\operatorname{Recall}}
  {\operatorname{Precision}+\operatorname{Recall}}.
\end{align}
We report both complete-graph and patch-changed node and edge metrics. When both expected and predicted changed sets are empty, the case is an exact match but contributes no positive item to the aggregate TP/FP/FN counts.

Classification agreement is measured across all ten cases. Rule-set agreement is measured on the three violation cases. File and exact-line agreement are measured on the five finding-bearing cases; exact-line agreement means that at least one evidence item for the matched finding has the expected file and line. Determinism requires byte-identical normalized output across the two executions of each input.

\subsection{Acceptance Criteria}

Before reporting the run, the engineering exit gate required node and edge precision and recall of at least 0.85 for both complete and changed graphs, exact classification for every case, exact violated-rule sets, matching evidence files and lines, deterministic replay, and repository-specific coverage thresholds. The value 0.85 is an engineering prototype threshold rather than a statistically derived standard; the raw counts and exact denominators are therefore reported alongside it.

\textbf{RQ1: graph reconstruction.}
The unchanged repository was reconstructed as five components and five relationships with a no-impact classification. Table~\ref{tab:detection-results} reports no false positive or false negative in the controlled cases. The full-graph totals aggregate 53 expected nodes and 54 expected edges across ten patched repositories. Changed-graph totals are much smaller: three node changes and six edge changes.

\textbf{RQ2: change classification.}
ArchSync matched all ten labels: five no-impact, three violation, and two evolution cases. It also matched the complete expected rule-identifier set for all three violations. Redis and AMQP additions were classified as evolution rather than violation, preserving a human-review path.

\textbf{RQ3: evidence localization.}
All five finding-bearing cases contained the expected file and at least one evidence item at the exact expected line. The three violation cases pointed to either the introducing call site or, for a missing required edge, a deterministic component anchor. The two evolution cases pointed to Redis or AMQP operations. The metric does not evaluate uniqueness or ranking when multiple evidence items exist.

\textbf{RQ4: determinism and reproducibility.}
The baseline and all ten cases produced byte-identical normalized JSON across duplicate executions. Thus one evaluation comprised 22 analyzer executions with no replay mismatch. A separate clean-clone verification on Windows reproduced the stored result and all repository quality gates. GitHub Actions independently reproduced the full benchmark and stored result on both \texttt{ubuntu-latest} and \texttt{windows-latest}.

\section{Discussion}

The experiment provides a positive feasibility result for the defined TypeScript/Node.js slice. For RQ1, deterministic AST detectors reconstructed every expected node and edge represented by the benchmark. For RQ2, the rule engine correctly gave violation precedence over topology evolution, while the REVIEW path avoided treating every new technology as forbidden. For RQ3, source locations made findings inspectable without asking a reviewer to rediscover the relevant call. For RQ4, normalized ordering and evidence deduplication removed observed replay variation.

The perfect scores must be interpreted with the denominators in Tables~\ref{tab:detection-results} and~\ref{tab:outcome-results}. Five no-impact cases contain no changed graph items. Only three changed nodes, six changed edges, three violation rule sets, and five finding-bearing cases exercise the corresponding positive outcomes. Moreover, the benchmark and analyzer were co-developed. The result is strong evidence that the implemented contracts and regression scenarios agree, but it is not an unbiased estimate of performance on unseen repositories.

The three-way decision is practically significant even in this small study. Cases that bypassed architectural rules were blocked, whereas Redis and AMQP additions were surfaced for review. This distinction supports architecture evolution without silently rewriting the expected model. Missing-edge evidence also exposes an inherent limitation: because an absent call has no call site, ArchSync anchors the finding to a deterministic source location in the responsible component.

A stronger next experiment should freeze the current analyzer, construct a blinded holdout set through an independent reviewer, and evaluate at least one real TypeScript repository. Challenge cases should include aliased imports, wrapper libraries, dynamic endpoint construction, dependency injection, monorepo layouts, generated code, unsupported Redis operations, and runtime-only dependencies. Performance and developer-comprehension measurements should be added only after correctness is tested on that broader corpus.

\section{Threats to Validity}

\textbf{Construct validity.}
Node, edge, classification, and evidence measures capture detectable topology and explicit rules, not component responsibility, architectural rationale, or runtime quality attributes. Exact-line agreement requires at least one matching evidence item and does not measure ranking, completeness of all supporting locations, or reviewer effort. Full-graph counts repeatedly include baseline structure, so changed-graph counts are necessary for interpretation.

\textbf{Internal validity.}
The authors curated both analyzer and benchmark. Although topology intent was established in Phase 1, executable patches and exact evidence lines were refined during Phase 2 integration. This creates benchmark-tuning and confirmation risks. Schema checks, mutation tests, independent patch application, hash binding, and raw per-case predictions prevent accidental inconsistency but do not provide an independent ground-truth judgment.

\textbf{External validity.}
The study contains one small synthetic TypeScript/Node.js system and ten changes. Detectors cover selected \texttt{fetch}, \texttt{pg}, Redis, and AMQP patterns. Results may not generalize to wrapper libraries, dynamic endpoints, reflection, dependency injection, unconventional monorepos, generated code, other languages, infrastructure-as-code, or runtime-only relationships.

\textbf{Conclusion validity.}
The benchmark has only three positive changed-node items, six positive changed-edge items, three violation rule sets, and five evidence-bearing cases. Perfect agreement on these counts is a feasibility and regression result, not a statistical claim about a population. No confidence interval or significance test is meaningful for the current development set.

\textbf{Reliability.}
Dependencies and inputs are pinned and hashed, paths and JSON are normalized, patches are isolated, and every input is executed twice. A clean local Windows clone reproduced the result with Node.js 22.16.0 and pnpm 11.16.0. GitHub Actions additionally reproduced the full benchmark on clean \texttt{ubuntu-latest} and \texttt{windows-latest} runners at commit \texttt{278019c06929} using SHA-256-verified artifacts built from the pinned Core and Guardian revisions. These controls reduce, but do not eliminate, platform and toolchain threats; the study still uses one Node.js major version and one pnpm version.

\section{Conclusion and Future Work}

ArchSync implements a deterministic bridge between a declared architecture contract and a source-derived TypeScript service graph. In the controlled ten-patch Order Platform benchmark, it achieved 1.000 precision, recall, and F1 for aggregate full and changed node and edge detection, classified 10/10 cases, matched 3/3 violation rule sets, localized 5/5 finding-bearing cases to the expected file and line, and reproduced all outputs across duplicate executions.

These numbers demonstrate that the current contracts, detectors, and benchmark scenarios operate coherently; they do not establish general accuracy because the development benchmark is small and co-evolved with the implementation. The immediate research priority is therefore an independently curated holdout evaluation on additional TypeScript systems and toolchain versions. Engineering work will extend analysis to Git diffs, pull-request annotations, and merge gates while preserving the deterministic result as the authoritative decision. Later studies should investigate unsupported language patterns, scalability, false-positive and false-negative causes, evidence comprehension, and architect decision time.

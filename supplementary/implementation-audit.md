## Verification of detector semantics against the pinned source

All line numbers below refer to `git show <revision>:<path>`, not the evolving worktree.

- Guardian `src/analyzer.ts:225`: `importBindings` records named and aliased `Client`/`Pool` imports from `pg`, and default/namespace imports. This tracks local identifier spellings, not compiler-resolved symbols.
- Guardian `src/analyzer.ts:141`: `targetFromUrl` maps `postgres:`/`postgresql:` URLs to lower-case hostname IDs, a `data` relationship and database component type. Database names/ports are not separate target IDs.
- Guardian `src/analyzer.ts:164`: `targetFromEnvironment` maps `DATABASE_URL` to the conventional target `postgres`; it does not read deployment-time environment values.
- Guardian `src/analyzer.ts:181`: `expressionEndpoint` resolves literals and previously mapped identifiers. For binary expressions it tries the right side first, regardless of operator; this is a deterministic heuristic, not faithful runtime branch evaluation.
- Guardian `src/analyzer.ts:352`: `variableEndpoints` collects declarations and runs four passes. A recognized constructor with an inline `connectionString` option populates `pgResources` under the declared identifier. The map is per file, not scope-sensitive symbol analysis. Wrapper-return values, arbitrary assignments, inter-file client flow and comprehensive alias/shadow resolution are not implemented by this map.
- Guardian `src/analyzer.ts:525`: a property call whose method is `query` yields a PostgreSQL observation only when its simple identifier receiver is in `pgResources`. A bare construction without a query emits no PostgreSQL edge. The evidence is anchored to the call expression; the confidence value `0.99` is fixed metadata, not a calibrated probability.
- Guardian `src/analyzer.test.ts`: positive alias/namespace tests and the test named “does not treat unrelated query, cache or publish methods as infrastructure access” document the intended discrimination. Tests were inspected for these claims; this audit does not imply a new run of the benchmark.

## Verification of gate and rejection semantics

- Core pinned `src/conformance.ts:306–329`: all violated deny/allow/require/require-path rules are accumulated, evolution findings remain in the result, and any rule violation wins the top-level classification. Rule severity is retained but is not used as a gate threshold.
- Guardian pinned `src/phase3.ts:139`: semantic keys use finding kind, rule/change/component/edge identity rather than source line position alone.
- Guardian pinned `src/phase3.ts:439–460`: differences between base/head finding identities yield introduced findings. Any introduced non-evolution finding yields BLOCK; otherwise introduced evolution yields REVIEW; otherwise PASS.
- Guardian pinned `src/bin.ts:200–220`: the Git-diff command maps PASS/BLOCK/REVIEW to exit codes 0/1/3. Source annotations/report formats do not themselves configure repository branch protection.
- Guardian pinned `src/phase3.ts:549–554`: REVIEW instructions request architecture approval before merge/model update. There is no approval/rejection input, persistent rejection ledger, or automatic model rewrite in this evaluated command. A rejected change with identical inputs remains REVIEW. Rejection must be enforced through repository review/merge controls; code revision/removal and rerun can remove the finding. New architecture requirements can be represented as explicit reviewed rules, but the tool does not generate those rules from rejection.
- Newer local development includes `src/evolution/approval.ts`, absent from the pinned runtime tree. Its existence must not be retrospectively claimed as a measured Phase 3 approval workflow.

\section{Implementation}

\subsection{Implemented Prototype}

The implementation is divided across three repositories used in this study. \archsyncrepository{archsync-core}{https://github.com/Little-Boy-s-ArchSync/archsync-core} implements Architecture Model version 0.1, JSON Schema and semantic validation, normalized graphs, graph difference, deny/allow/require/require-path semantics, command-line reports, and deterministic Mermaid and draw.io projections. The roadmap called this Phase 1 planning milestone v0.0; model version 0.1 is the first executable contract rather than a change of phase scope. At audit commit \texttt{f7812c4}, its current verification suite contains 114 tests, enforces 100\% statement, branch, function, and line coverage for the deterministic engine, and exercises 17 built-CLI smoke checks. Coverage here is a software-verification measure and is not empirical accuracy evidence.

\archsyncrepository{archsync-guardian}{https://github.com/Little-Boy-s-ArchSync/archsync-guardian} version 0.3 implements Observed Graph and Finding Contract version 0.1 with analyzer implementation version 0.2. The package number differs from the roadmap's planning label v0.2 because v0.2 was used for provenance-aware analyzer hardening before the PR gate; the Phase 3 scope is unchanged. The analyzer traverses TypeScript files, maps component roots, parses syntax trees through the TypeScript Compiler API, resolves explicit literals and selected environment-variable fallbacks, runs HTTP/PostgreSQL/Redis/AMQP detectors, captures evidence, and sorts and deduplicates output. The Phase 3 module invokes Git without a shell, reconstructs base source snapshots, validates or rebuilds graph-cache entries, maps changed paths to components, merges partial observations, compares stable finding identities, and renders human, JSON, Markdown, and GitHub-annotation outputs. Guardian delegates graph difference and rule semantics to Core. The pinned evaluation revision contains 58 tests, enforces 100\% statement, branch, function, and line coverage for the deterministic engine, and exercises 22 built-CLI smoke checks. These counts describe the immutable runtime artifact used for the controlled measurements, not later distribution-hardening revisions or analyzer accuracy on external systems.

\archsyncrepository{archsync-benchmark}{https://github.com/Little-Boy-s-ArchSync/archsync-benchmark} provides the synthetic Order Platform, 20 executable unified-diff patches, the group-authored ground-truth manifest, a 40-signal TypeScript challenge corpus, integrity validation, mutation tests, and evaluation runners. The patches are real executable diffs, but the system, cases, and labels are controlled research artifacts rather than changes sampled from an external project. Phase 2 applies each patch to a fresh temporary copy; Phase 3 initializes that copy as a Git repository, commits the baseline, applies the patch as a working-tree diff, performs cold and warm checks, and runs a separate full scan as an equivalence oracle for the incrementally reconstructed head. Signal annotations bind detector, file, exact line, expected edge, and a required source substring. Its validation libraries are exercised by 55 tests, including dynamically enumerated ground-truth mutations, while process-level validators and evidence verifiers cover the complete executable protocol. \texttt{archsync-mcp} is not used in the experiment.

\subsection{Reproducibility Controls}

The benchmark pins \archsynccommit{Core}{https://github.com/Little-Boy-s-ArchSync/archsync-core}{2affbbb0da859a32b9b9079b4bf718fc7b14993b}{2affbbb0da85} and \archsynccommit{Guardian}{https://github.com/Little-Boy-s-ArchSync/archsync-guardian}{8779bf7965b3bd15f25834f17ca5321c85ae3f43}{8779bf7965b3}. These are the runtime artifacts used to generate the reported measurements; later audit and documentation commits do not silently replace them. The end-to-end manifest records SHA-256 values for the architecture model, nine-file baseline tree, and 20-patch set. Phase 3 evidence additionally hashes the Guardian v0.3 package and normalized Git-diff results while recording the cache protocol, incremental scope, environment, and raw timing samples. Its verifier recomputes derived timing statistics and rejects any incremental result that differs from the full-scan oracle or declared architecture delta. Core's Phase 1 evidence binds production source, tests, the complete fixture tree, verification configuration, package metadata, and lockfile. Guardian's Phase 2 and Phase 3 evidence similarly binds implementation and verification source, fixture trees, package metadata, lockfile, and the pinned Core artifact. The challenge evidence separately hashes its signal manifest, architecture, source tree, normalized result, and analyzer package. The benchmark workflow passed at audit commit \texttt{24d63eb}, the Guardian workflow passed at \texttt{8779bf7}, and the portable Core evidence workflow passed at \texttt{e3d050e} without changing the pinned runtime package.

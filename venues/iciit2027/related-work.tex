\section{Background and Related Work}
This scoped narrative review positions ArchSync against foundational and contemporary conformance approaches using sources selected purposively from the retained keyword-search corpus. Contemporary evidence is from 2022--2025; two older references establish the origins of model comparison and dependency constraints.

\textbf{Problem and observation boundary.} A recent mapping characterizes architecture erosion \cite{li2022erosion}. Code-review studies identify symptoms in OpenStack and OpenStack/Qt projects \cite{li2022symptoms,li2023warnings}; their project overlap limits independence. Practitioner evidence identifies documentation and shared practices as ways to manage drift \cite{anthony2024drifting}. A recovery taxonomy and microservice-tool mapping distinguish reconstruction purposes and applicability \cite{sar2024taxonomy,bakhtin2024mapping}. View-based drift analysis compares intended and reconstructed specifications in an industrial case \cite{uzun2024drift}. These works motivate an explicit observation boundary between a source graph and the runtime architecture.

\textbf{Closest conformance approaches.} Software Reflexion Models establish high-level/source model comparison \cite{murphy1995reflexion}, and Dependency Constraint Language develops declarative dependency constraints \cite{terra2009dcl}. ArchSync builds on these concepts. CALint checks Python dependencies against Clean Architecture rules \cite{calint2022}. ArchLintor detects TypeScript module-interaction violations, provides source-linked diagnostics and describes CI/CD integration \cite{archlintor2025}. ArchSync's contribution combines typed service interactions, their source evidence and Git-time introduced-finding decisions. For example, changing a fetch destination can change a service relationship while leaving module imports unchanged. Linking that relationship to a rule and a source location makes the architectural consequence inspectable; comparing base and head distinguishes an introduced violation from a new relation requiring an architecture decision. LLM-generated architectural tests introduce a further rule-translation step \cite{lucena2025gatekeepers}; ArchSync executes explicitly supplied deterministic rules.

\textbf{Change-time feedback and verification.} Repository mining studies microservice evolution \cite{evolution2024}, and industrial conformance visualization reports practitioner experience \cite{thermofisher2025}. ArchSync uses relationship-level keys to keep existing findings visible while directing Git-time decisions to newly introduced findings. Evaluation-method research stresses replicability \cite{konersmann2022replicability}; interrogation testing shows that targeted inputs can expose analyzer soundness and precision failures \cite{kaindlstorfer2024interrogation}. Retained failure/repair evidence makes the implementation of this combined workflow inspectable.

\textbf{Published evidence and integration value.} Table~\ref{tab:external} compares the approaches at their reported observation units. ArchLintor illustrates module-level absence and divergence; CALint's publisher abstract reports three cases. Schneider et al. execute nine recovery tools on 17 Java/Spring applications \cite{schneider2025comparison}, providing a design for recovery evaluation. ArchSync connects selected HTTP, PostgreSQL, Redis and AMQP observations to an explicit service contract and a base/head decision with source evidence. The useful combination is a traceable path from a changed service interaction to BLOCK or REVIEW, backed by retained regression and failure/repair records. Section~\ref{sec:validity} defines the scope of these records and the remaining comparative requirement.
